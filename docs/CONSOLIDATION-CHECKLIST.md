## Security Concerns

**No active vulnerabilities found.** Specifically verified clean:
- All 26 `app/api/**/route.ts` handlers derive identity via `ensureAppUser()`/`getCurrentSupabaseUser()` — zero instances of a route trusting a client-supplied `user_id`.
- Zero `"use client"` files import `lib/repositories` or `lib/db` — every repository file is guarded by `import "server-only"` as its first line.
- `DATABASE_URL` usage confined to `lib/db/index.ts`, correctly never `NEXT_PUBLIC_`-prefixed.
- No `SUPABASE_SERVICE_ROLE_KEY` usage found anywhere in this repo.
- No SQL-injection risk found — all `sql.unsafe()` calls interpolate hardcoded constant column-list strings, never user input.

**Items to carry forward as design constraints, not current bugs:**
- The two `NEXT_PUBLIC_MONEY_FLOW_SUPABASE_*` env vars are publishable/anon keys (not secrets) but represent a legacy second-login surface that should be retired once Phase 5 confirms it's safe (tracked above).
- Money Flow's recurring-transactions cron has a real, exploitable-by-accident duplicate-write bug (no idempotency) — do not port that code path as-is; see Finance section.
- No middleware.ts exists — all auth gating is per-route via `ensureAppUser()`. This works today (verified 26/26 routes comply) but has no structural backstop if a future route is added without remembering to call it; consider adding a lint rule or middleware-level check as the API surface grows past ~30 routes.
- Google Calendar refresh tokens (once ported) must land behind a repository-boundary convention equivalent to Hengo's service-role + column-grant trick — Neon has no PostgREST/RLS layer to enforce this automatically, so it becomes a code-review discipline rather than a database-enforced guarantee.

## Recommended Implementation Order

This matches the product brief's PR sequence (PR A–J) and phase order; the audit didn't surface anything that should reorder it. Sequencing rationale based on what this audit found:

1. **PR A — DB verification + Reminders (Phase 1-2).** DB state is unverified but low-risk (idempotent migrations); Reminders is the single highest-priority missing feature and has no dependency on anything else missing.
2. **PR B — Today 2.0 (Phase 3).** Cheap to build now — Habits and Finance summary data already exist server-side; only Reminders (from PR A) and Learning due-counts need wiring in.
3. **PR C — Neon cutover verification + legacy adapter removal (Phase 4-5).** Confirm real data (Finance/Learning) looks right, then delete the 9 confirmed-orphaned files/env-vars listed above. Pure cleanup, no functional risk since nothing imports them.
4. **PR D — Goals 2.0 + Next Action (Phase 6-7).** Start here specifically because it's the highest schema-risk item (`goals`/`tasks` have no Hengo migration file) — better to absorb that reverse-engineering cost early while the audit context is fresh, rather than let it block later phases.
5. **PR E — Planner + Google Calendar (Phase 8-9).** Google Calendar's OAuth/token code is the most directly portable integration in either source repo — low risk, high polish value.
6. **PR F — Learning core parity (Phase 10, excluding Korean Coach voice and Interview content decision).** Nearly all schema already exists in Neon; this is mostly service/repository/UI construction, not schema design. Tackle in the brief's stated sub-order (Vocabulary modes → Foundations → Phrasebook → Reading → Listening → Scenarios → Progress), deferring Interview practice until the content-reuse question (K-Specialist exam scope) is explicitly decided.
7. **PR G — AI foundation + text-based Interview/Korean Coach (Phase 11-12).** Port Hengo's `requireUser`/rate-limit/structured-output pattern once, reuse for every AI consumer. Explicitly exclude Realtime voice coaching from this PR — schedule it as its own initiative given the WebRTC/ephemeral-token engineering lift.
8. **PR H — Finance automation + reports (Phase 13).** Build Recurring Transactions and Reports fresh (don't port Money Flow's buggy recurring-cron logic; do copy its `monthly_report_deliveries` idempotency pattern). AI Money Coach is the highest-value single port in the audit — prioritize it within this PR once Phase 11 lands.
9. **PR I — MCP + integrations (Phase 16-18).** Hengo's MCP OAuth-issuer design may need less rework than expected since HeangOS also uses Supabase as its Auth issuer — worth scoping early even though it's sequenced late.
10. **PR J — Docs + tests + cleanup + migration verification (Phase 19-27).** `docs/ARCHITECTURE.md` and `docs/APP-MIGRATION.md` are already stale today (describe a dual-Supabase-session design the code has moved past) — this cleanup is overdue, not just a final step; consider doing a lightweight doc fix in PR C alongside the legacy-adapter removal rather than waiting until the very end.
